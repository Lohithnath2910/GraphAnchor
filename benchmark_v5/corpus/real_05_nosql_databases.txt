NoSQL Databases: Concepts and Characteristics

What is NoSQL? NoSQL Database is a non-relational Data Management System, that does not require a fixed schema. It avoids joins, and is easy to scale. The major purpose of using a NoSQL database is for distributed data stores with humongous data storage needs. NoSQL is used for Big data and real-time web apps. For example, companies like Twitter, Facebook and Google collect terabytes of user data every single day.

NoSQL database stands for "Not Only SQL" or "Not SQL." Though a better term would be "NoREL", NoSQL caught on. Carl Strozz introduced the NoSQL concept in 1998. Traditional RDBMS uses SQL syntax to store and retrieve data for further insights. Instead, a NoSQL database system encompasses a wide range of database technologies that can store structured, semi-structured, unstructured and polymorphic data. Horizontal Scaling As data grows, NoSQL can spread data across multiple computers. Imagine a library. One librarian can handle only so many visitors. If visitors increase, you hire more librarians. Similarly: Vertical scaling = Buy one bigger, more powerful computer. Horizontal scaling = Add more computers to share the work. This makes NoSQL suitable for websites like Facebook, Amazon, and Netflix.

Fast Queries NoSQL databases are designed to retrieve data quickly.

Example: If a shopping app wants all details of one customer, NoSQL often stores everything together, making it faster to read.

Easy for Developers Developers can easily store different kinds of data without redesigning the database every time. Example: Today a product has: Name Price Tomorrow you want to add: Color Size Brand In NoSQL, this is usually much easier.

With microservices and NoSQL, you can scale only the Product Service by adding more servers, instead of scaling the entire application.

Why NoSQL Works Well with Microservices Independent Updates If you want to add a new field like discount to products, you only update the Product Service. You don't need to change the User or Order Services.

Why NoSQL? The concept of NoSQL databases became popular with Internet giants like Google, Facebook, Amazon, etc. who deal with huge volumes of data. The system response time becomes slow when you use RDBMS for massive volumes of data. To resolve this problem, we could "scale up" our systems by upgrading our existing hardware. This process is expensive. The alternative for this issue is to distribute the database load on multiple hosts whenever the load increases. This method is known as "scaling out."

NoSQL database is non-relational, so it scales out better than relational databases as they are designed with web applications in mind.

Types of NoSQL Databases NoSQL Databases are mainly categorized into four types: Key-value pair, Column-oriented, Graph-based and Document-oriented. Every category has its unique attributes and limitations. None of the above-specified database is better to solve all the problems. Users should select the database based on their product needs. Types of NoSQL Databases: Key-value Pair Based Column-oriented Graph Graphs based Document-oriented

Key Value Pair Based Data is stored in key/value pairs. It is designed in such a way to handle lots of data and heavy load. Key-value pair storage databases store data as a hash table where each key is unique, and the value can be a JSON, BLOB(Binary Large Objects), string, etc. For example, a key-value pair may contain a key like "Website" associated with a value like "Guru99".

Document-Oriented Document-Oriented NoSQL DB stores and retrieves data as a key-value pair but the value part is stored as a document. The document is stored in JSON or XML formats. The value is understood by the DB and can be queried. In this diagram on your left, you can see we have rows and columns, and in the right, we have a document database which has a similar structure to JSON. Now, for the relational database, you have to know what columns you have and so on. However, for a document database, you have a data store like a JSON object. You do not need to define what makes it flexible. The document type is mostly used for CMS systems, blogging platforms, real-time analytics & e-commerce applications. It should not be used for complex transactions which require multiple operations or queries against varying aggregate structures.

Document-Oriented stores data as documents instead of rows and columns like a relational (SQL) database. A document is usually stored in JSON (JavaScript Object Notation), BSON (Binary JSON), or XML format.

Advantage is that each document can have its own structure, so you don't have to define a fixed schema before storing data.

In a SQL database, every student must have the same columns. Suppose a new student joins and also has a scholarship.

In SQL, you would need to add a new column (Scholarship) to the table, even though most students don't have one.

What is a Document? A document is a collection of key-value pairs.

Storing Nested Data documents can contain nested objects Suppose every student has an address.

In SQL, this might require another table and a JOIN operation.

In a document database, it is stored together in one document.

Advantages Flexible schema: Documents can have different fields. Supports nested data: Objects and arrays can be stored directly. Easy to modify: Add new fields without changing existing documents. Rich queries: Search using any field, not just a key. Scalable: Suitable for applications with growing and changing data.

Disadvantages Data may be duplicated across documents. Managing relationships between different documents can be harder than in SQL databases.

Real-World Applications Document databases are commonly used for: E-commerce websites: Products with different attributes (size, color, brand, warranty, etc.). Content Management Systems (CMS): Articles where each article may have different sections, tags, or metadata. User profiles: Different users may provide different information. Mobile applications: App data structures often change as features are added. Blog websites: Each post can have a different number of comments, tags, and images.

Graph-Based A graph-type database stores entities as well as the relations amongst those entities. The entity is stored as a node with the relationship as edges. An edge gives a relationship between nodes. Every node and edge has a unique identifier. Compared to a relational database where tables are loosely connected, a Graph database is a multi-relational database in nature. Traversing relationships is fast as they are already captured in the DB, and there is no need to calculate them. Graph-based database is mostly used for social networks, logistics, and spatial data. Neo4J, Infinite Graph, OrientDB, and FlockDB are some popular graph-based databases.

A Graph Database stores data as nodes, relationships (edges) and properties. It is designed to efficiently represent and query connected data. Designed to manage interconnected data. Uses Neo4j, Amazon Neptune and JanusGraph for graph processing. Stores relationships as edges for direct navigation between connected nodes.

Components of a Graph Database

Nodes (Vertices) entities or objects in the graph. Each node can store properties that describe the entity Examples: Person Customer Product City Example (Person: John)

Relationships (Edges) connect two nodes and represent how they are related. They define the connections between entities. Examples: FRIENDS_WITH PURCHASED WORKS_FOR LOCATED_IN

Properties (Attributes) key-value pairs that store additional information about nodes and relationships. Examples: Name = "John" Age = 25 Since = 2022

Labels Labels categorize nodes into different groups, making it easier to organize and query data. Examples: Person Employee Customer Product

A node can have one or more labels

Step 1: Identify the Nodes Nodes represent the entities in the graph. In the diagram: Alice Bob Carol Eve Acme Corp Product X

These are all nodes because they represent people, an organization and a product.

Step 2: Identify the Relationships Relationships connect nodes and describe how they are associated. Alice is connected to Bob and to Carol through a FRIENDS_WITH relationship, to Acme Corp through a WORKS_AT relationship, and to Product X through a PURCHASED relationship These relationships directly connect related entities.

Step 3: Identify the Properties Properties store additional information about nodes. In the diagram: Alice: Age = 28, City = New York Bob: Age = 30, City = Boston Carol: Age = 27, City = Chicago Eve: Age = 24, City = Seattle Acme Corp: Industry = IT, Location = USA Product X: Category = Electronics, Price = $699

Step 4: Traverse the Graph When a query is executed, the graph database follows relationships directly to retrieve connected data instead of performing JOIN operations. Example: To find Alice's friends, the database follows the FRIENDS_WITH relationships and returns Bob and Carol.

To find where Alice works, it follows the WORKS_AT relationship and returns Acme Corp.

To find what Alice purchased, it follows the PURCHASED relationship and returns Product X.

Uses of Graph Databases widely used in applications where relationships between data are important. Social Networks: Manage user connections and friendships. Recommendation Systems: Suggest products, movies or friends based on user preferences. Fraud Detection: Detect suspicious connections and fraudulent activities. Knowledge Graphs: Organize connected information for better search and analysis.

Column-based Column-oriented databases work on columns and are based on BigTable paper by Google. Every column is treated separately. Values of single column databases are stored contiguously. They deliver high performance on aggregation queries like SUM, COUNT, AVG, MIN, etc., as the data is readily available in a column. Column-based NoSQL databases are widely used to manage data warehouses, business intelligence, CRM, Library card catalogues, HBase, Cassandra, HBase, Hypertable are NoSQL query examples of column-based databases.

These databases store data in columns instead of rows.

What is the CAP Theorem? CAP theorem is also called brewer's theorem. It states that is impossible for a distributed data store to offer more than two out of three guarantees Consistency Availability Partition Tolerance Consistency: The data should remain consistent even after the execution of an operation. This means once data is written, any future read request should contain that data. For example, after updating the order status, all the clients should be able to see the same data. Availability: The database should always be available and responsive. It should not have any downtime. Partition Tolerance: Partition Tolerance means that the system should continue to function even if the communication among the servers is not stable. For example, the servers can be partitioned into multiple groups which may not communicate with each other. Here, if part of the database is unavailable, other parts are always unaffected.

Eventual Consistency The term "eventual consistency" means to have copies of data on multiple machines to get high availability and scalability. Thus, changes made to any data item on one machine has to be propagated to other replicas. Data replication may not be instantaneous as some copies will be updated immediately while others in due course of time. These copies may be mutually, but in due course of time, they become consistent. Hence, the name is eventual consistency. BASE: Basically Available, Soft state, Eventual consistency Basically, available means DB is available all the time as per CAP theorem Soft state means even without an input; the system state may change Eventual consistency means that the system will become consistent over time
